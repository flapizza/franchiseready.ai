# Production Persistence Foundation

Status: architecture audit and migration plan only. This document deliberately contains no SQL or migration implementation.

## 1. Executive assessment

FranGroove has good persistence seams in Candidates, Pipeline, Tasks, Calendar, and Brand Library, but it does not yet have production business persistence. Supabase currently provides authentication/session scaffolding only. Business state is assembled from deterministic TypeScript fixtures plus one process-local `globalThis` overlay. A restart loses mutations; multiple application processes can disagree; and authorization is mostly a demo-consultant equality check rather than database-enforced tenancy.

The safest direction is an organization-owned relational core with hierarchical candidate authorization, UUID primary keys, stable route slugs/public IDs, append-only domain history, and repository adapters selected explicitly at application composition. Organization membership establishes tenancy; candidate assignment and reporting ancestry establish visibility inside the tenant. Candidate intelligence, briefings, queues, scores, and Mission Control cards must not all become columns: persist evidence, consultant decisions, versioned outputs where reproducibility matters, and recompute presentation projections.

The existing application should migrate by bounded feature packs. Each pack introduces repository contracts or durable adapters for one dependency slice while retaining an explicit demo tenant and deterministic fixtures. Do not use request-dependent, implicit fallback from Supabase to the process-local overlay in production.

## 3. Existing Supabase foundation

- Installed: `@supabase/ssr` 0.12.4 and `@supabase/supabase-js` 2.111.0.
- Browser client: `lib/supabase/browser.ts`, publishable key, SSR-compatible browser cookies.
- Server client: `lib/supabase/server.ts`, request cookies and safe handling when Server Components cannot write cookies.
- Proxy client: `lib/supabase/proxy.ts`; refreshes cookies and uses `auth.getClaims()` rather than trusting local storage.
- Admin client: `lib/supabase/admin.ts`; service-role key, server-only, session persistence/refresh disabled. It exists but has no current caller.
- Auth: email/password sign-up/sign-in/sign-out, PKCE callback exchange, reset/update password, generic reset response, Zod input validation, safe same-origin return paths.
- Proxy: protects route prefixes and preserves refreshed session cookies across redirects. Conference demo bypass is development/Playwright-only and requires an explicit environment flag plus HTTP-only cookie.
- Environment: Zod validates URL/publishable key/application URL and separately validates the service-role key. There is no database-specific configuration or deployment/startup validation beyond on-demand parsing.
- Database: `supabase/migrations` and `supabase/seed` contain only `.gitkeep`; no schema, generated `Database` type, RLS policies, functions, storage policies, local Supabase config, or migration test harness exists.
- Account model: application auth exposes only `{id,email}`. There are no user profiles, organizations, memberships, roles, active-workspace selection, invitations, or provisioning trigger.

Assessment: auth/session code is a useful production foundation. Business authorization, account provisioning, typed database access, operational migrations, and RLS are scaffolding gaps, not small adapter work.

## 4. Recommended tenancy and ownership model

Use `auth.users` as authentication identity and a public `user_profiles` row as application identity. A user may belong to multiple organizations through `organization_memberships`. `consultant_profiles` represents consultant-specific attributes and references a user; organization-specific role, status, and reporting position belong on the membership, not the profile.

Authorization has two explicit boundaries:

1. **Outer tenant boundary — organization.** Every tenant business row carries a non-null `organization_id`, even when reachable through a candidate. Active organization membership is necessary but does not itself grant candidate access.
2. **Inner candidate boundary — assignment plus reporting hierarchy.** A consultant sees candidates assigned to their own membership. A manager/team leader sees their own candidates plus candidates assigned to active descendant memberships in the same organization. Peers do not see one another. Owners/admins may receive organization-wide administrative visibility through explicit role policy.

Candidate assignment is therefore both operational responsibility and an authorization boundary. `candidates.assigned_consultant_membership_id` is non-null for ordinary active candidates; an explicit team/unassigned queue would require a separately approved policy rather than a null assignment silently broadening access. Candidate-dependent records inherit the candidate boundary, even when addressed directly by their own ID.

Use a simple tree for beta: `organization_memberships.manager_membership_id` self-references another active membership in the same organization. This is preferable to a separate current `reporting_relationships` table because each membership has at most one manager, the approved model is a tree, reassignment is a single current relationship change, and recursive ancestor/descendant checks are direct. Index `(organization_id, manager_membership_id)`. Mutations must reject self-management, cross-organization parents, and cycles. Preserve manager changes in append-only `membership_reporting_history`. A separate relationship table should be introduced only if matrix/shared management becomes a real requirement.

The hierarchy supports Owner → Regional Manager → Team Leader → Consultant without requiring all levels in the beta UI. Treat `owner`, `admin`, and `consultant` as the minimal durable roles. Manager/team-leader behavior is primarily a consultant membership with descendants plus a bounded management capability, not a rigid global title; this permits regional/team levels without creating dozens of roles. Future read-only, support, and custom capabilities remain additive.

Organization, user identity, membership/hierarchy, subscription/billing identity, white-label identity, and connected provider accounts remain separate aggregates. A one-consultant beta organization must not collapse them. Organization settings own standardized pipeline definitions, shared Brand Library visibility, and retention policy. White-label branding has its own organization-owned record; subscription has its own billing reference; provider accounts attach primarily to individual memberships. Consultant preferences own timezone, notification, signature, filters, ordering, saved views, and display preferences.

Pipeline **configuration** and **content** are distinct. Beta canonical stage definitions are standardized at organization/team level. Pipeline content is the candidates visible through assignment/hierarchy. A manager may select My Pipeline, an individual descendant, or All Team; this changes the authorized projection, not candidate ownership or canonical stages. Preserve future pipeline templates, team-specific configurations, inheritance, multiple pipelines, and consultant-specific configurations without implementing them in beta.

Reassignment changes only current assignment and access: the new consultant gains ordinary access and the previous consultant loses it unless a future explicit sharing/history policy says otherwise. The transaction records previous assignee, new assignee, actor, and timestamp. It never rewrites activities, communications, referrals, Discovery evidence, released intelligence, or other provenance. Ancestor access is always evaluated against the current hierarchy unless an audit-specific privileged view is explicitly authorized.

## 5. Proposed logical schema

All UUID tables include `created_at` and `updated_at` unless immutable. Tenant tables include indexed `organization_id`. Foreign keys should normally restrict deletion of audit-critical records; archive or redact instead of cascading history away.

### Identity and tenancy

- `user_profiles`: PK/FK `user_id -> auth.users`; display name, locale, platform status. One per auth user.
- `organizations`: UUID PK, unique slug, name, status, organization type, default timezone. Archive rather than delete. It is not the subscription, branding identity, membership, hierarchy, or provider account.
- `organization_memberships`: UUID PK; organization/user FKs, role, status, nullable same-organization `manager_membership_id`, bounded capabilities, invited/accepted timestamps; unique `(organization_id,user_id)`; indexes by user, active organization, and `(organization_id,manager_membership_id)`.
- `membership_reporting_history`: UUID PK; organization, membership, previous/new manager membership, actor membership, effective timestamp; append-only. It preserves restructuring history without making current RLS traverse historical relationships.
- `consultant_profiles`: UUID PK, unique user FK, professional/contact fields. Organization assignment remains membership-based.
- `organization_branding`: organization PK/FK, names/domains/theme/logo storage references. Domain ownership must be verified separately.
- `organization_subscriptions`: organization PK/FK plus external billing customer/subscription references, plan/status/period metadata. Billing identity remains independent of white-label and provider identities.

### Candidates, pipeline, and activity

- `candidates`: UUID PK; organization, stable `public_id`/slug, required assigned membership for ordinary active candidates, creator membership, names/contact, normalized email/phone, location, status, current stage FK, territory/source, archive timestamp. Unique `(organization_id,public_id)`; partial duplicate-detection indexes on normalized contact; do not globally require unique email. Assignment must reference the same organization.
- `candidate_assignment_history`: UUID PK; candidate/organization, previous/new assigned memberships, actor membership, reason, occurred timestamp; immutable and indexed by candidate/time.
- `candidate_notes`: UUID PK; candidate/organization, author membership, body, archived timestamp. Beta visibility inherits candidate authorization; do not add a private-note subsystem yet. Preserve room for a later visibility class.
- `pipelines`: UUID PK; organization, optional team scope for future use, name, default flag, archived timestamp. Beta uses standardized canonical configuration, not consultant-private lifecycle definitions.
- `pipeline_stages`: UUID PK; pipeline, stable key, label, order, enabled, canonical lifecycle mapping, classification, presentation metadata; unique `(pipeline_id,stable_key)` and `(pipeline_id,order)`.
- `candidate_stage_history`: UUID PK; candidate/organization, from/to stage, actor, source, reason, occurred timestamp; immutable and indexed `(candidate_id,occurred_at desc)`.
- `candidate_activities`: UUID PK; organization/candidate, event type, actor, source, source record type/id, title/description, constrained metadata JSONB, occurred timestamp; append-only. This is an activity feed, not the sole store of domain truth.

### Assessment, intelligence, and Discovery

- `assessment_definitions` and `assessment_versions`: UUID PKs; stable key, version, schema/content JSONB (appropriate because question payloads are versioned documents), status/effective timestamps; unique key/version.
- `assessment_invitations`: UUID PK; organization/candidate/version, opaque token hash (never raw bearer token), expiry/status/sent/completed timestamps; unique token hash.
- `assessment_attempts`: UUID PK; organization/candidate/version, respondent boundary, status, started/completed timestamps, scoring algorithm version.
- `assessment_responses`: UUID PK; attempt/question stable key, typed answer JSONB, answered timestamp; unique `(attempt_id,question_key)`.
- `assessment_results`: UUID PK; attempt, released result snapshot JSONB, algorithm/version, generated/released timestamps. JSONB is appropriate for a versioned immutable result document; searchable dimensions may be promoted later.
- `candidate_evidence`: UUID PK; organization/candidate, evidence kind/source, source record, original text/value JSONB, confidence, occurred/recorded timestamps, creator type and actor, review status. Immutable source evidence; corrections supersede rather than overwrite.
- `candidate_intelligence_versions`: UUID PK; candidate/organization, algorithm/prompt/model versions, input evidence watermark/hash, snapshot JSONB, status (`draft/released/superseded`), generated/reviewed/released actors/timestamps. Current released version may be referenced by candidate or selected by query.
- `candidate_intelligence_overrides`: UUID PK; intelligence version or fact key, consultant actor, prior/new value, rationale, timestamp. Preserve original AI output.
- `discovery_sessions`: UUID PK; organization/candidate, facilitator membership, status/stage, scheduled/started/completed timestamps, meeting event FK, summary and archive state.
- `discovery_events`: UUID PK; session/organization/candidate, type, source, source segment/reference, content, occurred timestamp, AI/consultant provenance. Append-only.
- `discovery_facts`: UUID PK; session/candidate, fact key/category, value JSONB, evidence FK, confidence, confirmation status, supersedes FK. Do not store only the runtime memory blob.
- `discovery_transcript_segments`: UUID PK; session, sequence, speaker, text, provider timing/reference, retention/redaction fields. Large media belongs in Storage; access follows the session tenant.

### Work management and calendar

- `tasks`: UUID PK; organization, candidate/brand/referral optional FKs, creator/assignee memberships, status/priority/due/completed fields, source/source ID/reason, archived timestamp; indexes on assignee/status/due and candidate.
- `task_status_history`: UUID PK; task/organization, from/to status, actor/source, occurred timestamp.
- `task_recommendation_decisions`: UUID PK; organization, stable recommendation key, candidate, action (`accepted/dismissed`), accepted task FK, actor/timestamp; unique `(organization_id,recommendation_key)`.
- `calendar_events`: UUID PK; organization, owner membership, optional candidate, title/body, start/end `timestamptz`, original IANA timezone, location/URL, source/status, recurrence rule JSONB where provider-neutral representation needs it, archived timestamp; indexes by owner/time and candidate/time.
- `calendar_event_tasks`: event/task join with unique pair; replaces embedded task ID arrays.
- `reminders`: UUID PK; organization, recipient membership, typed reference, remind timestamp, status/source; indexes for pending due work. Prefer explicit nullable FKs or separate join types over unconstrained IDs when practical.
- `calendar_event_history`: immutable event/status/provider conflict history.

### Strategy, presentation, and referrals

- `candidate_brand_strategies`: UUID PK; organization/candidate, status, created/updated/presentation timestamps; unique active strategy per candidate.
- `candidate_brand_decisions`: UUID PK; strategy/candidate/organization/brand, selected flag, order, reaction, notes, disposition, timestamps; unique `(strategy_id,brand_id)`. Outside brands do not belong here until they have an identity.
- `brand_presentations`: UUID PK; strategy/candidate/organization, facilitator, started/completed timestamps and status.
- `brand_presentation_events`: UUID PK; presentation/brand, reaction/note/action provenance and timestamp; retains revisions.
- `referrals`: UUID PK; organization/candidate, nullable global brand FK, immutable outside-brand identity/contact snapshot, source, status, recommendation/version references, consultant decision snapshot JSONB, created/approved/introduced timestamps; indexes candidate/status and brand/status.
- `referral_package_versions`: UUID PK; referral, version, content snapshot JSONB, editable subject/message/notes, generated provenance, approved actor/time; unique referral/version. JSONB is justified for the immutable rendered handoff document, while ownership/status remains relational.
- `referral_delivery_attempts`: UUID PK; referral/package version, idempotency key, provider/connected account, status, provider message ID, attempt/sent/failure fields, sanitized provider response metadata; unique organization/provider/idempotency key and provider message ID when present.

### Communications and providers

- `connected_accounts`: UUID PK; organization, owner membership, provider, provider account ID/email, scopes, status, token-secret reference/encrypted token columns, expiry/refresh timestamps; unique active provider account identity.
- `communication_threads`: UUID PK; organization/candidate, provider-neutral subject/context, optional provider thread identity through mapping table.
- `email_messages`: UUID PK; organization/candidate/consultant/thread, direction, sender snapshot, subject/body/format, status, tracking flags, related brand/referral/template, idempotency key, external-delivery flag; unique `(organization_id,send_idempotency_key)`.
- `email_recipients`: message FK, kind/name/email; index normalized email.
- `email_links`: UUID PK; message, original destination, label; never persist a provider rewrite as canonical URL.
- `email_delivery_attempts`: UUID PK; message/account, provider, status/timestamps/failure category/provider ID; unique provider message identity where available.
- `email_engagement_events`: UUID PK; organization/candidate/message/link, type, occurred timestamp, provider event ID, constrained metadata; append-only; unique `(connected_account_id,provider_event_id)` when present.
- `provider_webhook_receipts`: UUID PK; organization/account/provider/event ID, payload hash, processing status/timestamps/error; unique provider/account/event for idempotency. Retain raw payload only briefly and encrypted if required.
- `calendar_account_state`: connected account/calendar identity, sync token or delta link secret/reference, channel/subscription expiry, last sync, status; unique account/calendar.
- `calendar_provider_mappings`: canonical event/account/provider event ID, recurring master/instance IDs, etag/version, deleted flag, last synced; unique account/provider event ID.
- `background_jobs`: if the selected job platform lacks durable native records, store job type, tenant, idempotency key, status/attempts/schedule/error; otherwise keep only domain receipts locally.

### Brand Intelligence

- `brands`: global UUID PK, stable unique slug/public ID, canonical name/category/status; no organization owner.
- `brand_fact_versions`: UUID PK; brand, fact key, typed value JSONB, source/submission, approval, effective/verified timestamps, reviewer, supersedes FK. Index current approved facts by brand/key.
- `brand_materials`: UUID PK; brand, kind, storage/URL reference, approval and version metadata.
- `franchisor_submissions`: UUID PK; brand, submitter identity/organization if applicable, status, submitted/reviewed timestamps; submission items link to proposed facts.
- `organization_brand_settings`: organization/brand composite identity; visibility, private notes, relationship metadata. Sponsorship/commercial fields must live separately.
- `brand_commercial_relationships`: restricted table for sponsorship/commercial status. Recommendation/scoring queries and feature inputs must not join this table; add tests enforcing invariant output with commercial state changed.

## 6. Authorization and RLS model

RLS is mandatory on every exposed tenant table and evaluates both boundaries. Access requires (1) an active membership in the row's organization and (2) candidate authorization because the actor is the assigned membership, an active ancestor manager of that membership, or an owner/admin whose explicit policy grants organization-wide administrative access. Organization membership alone is never sufficient for candidate data.

Implement the descendant test behind one carefully reviewed database authorization helper used consistently by policies. It resolves the caller's active membership and traverses the current `manager_membership_id` tree within one organization. Bound recursion defensively and prevent cycles on hierarchy mutation. Cache/closure tables are not justified for beta; add one later only if measured policy performance requires it. Policies must not trust ancestry or organization IDs supplied by the client.

Direct child tables carry `organization_id` and a candidate FK where the domain is candidate-dependent. Policies verify organization consistency and access through the parent candidate. `USING` and `WITH CHECK` rules must prevent both reading a nested record and inserting/updating it under an unauthorized candidate. Repository methods also require authorization context and candidate ownership, but repository filtering supplements rather than replaces RLS.

- A consultant reads/writes their assigned candidates according to capability; peers in the same organization remain isolated.
- A manager/team leader reads their own and authorized descendants' candidates. Management writes such as reassignment require an explicit bounded capability. A manager cannot cross to another hierarchy branch.
- Owners/admins receive organization-wide administrative access only through explicit role policy, with sensitive operations audited.
- Candidate reassignment is atomic: authorize actor, change assignment, append assignment history/activity, and preserve all existing domain records unchanged.
- Candidate 360, intelligence, assessment/financial data, pipeline history, tasks, events/meetings/reminders, communications/engagement, Discovery, Strategy/Presentation, referrals, activities, and released snapshots all inherit candidate access. A discovered nested ID is never an authorization grant.
- Notes follow candidate authorization in beta: assigned consultant and authorized ancestors can read them; peers cannot. Private/restricted note classes are deferred.
- Sensitive financial, transcript, recording, credential, and provider-account tables may use narrower capability policies than ordinary candidate visibility.
- Service-role clients bypass RLS and must never be used for ordinary browser/server user requests. Create narrowly scoped server operations that validate tenant and actor before service-role work.
- Webhooks authenticate provider signatures, resolve a connected account to its organization, deduplicate receipt, and write through a narrowly scoped server function/worker. The provider payload never supplies trusted `organization_id`.
- Background jobs carry organization and source record IDs, re-resolve ownership, and use idempotency keys. Prefer security-definer database functions only when necessary, with fixed search paths and minimal grants.
- Public assessment access uses an opaque, expiring, resumable, revocable, single-purpose token whose hash is stored. It permits only the named assessment attempt and safe question/completion operations; it does not create an authenticated organization member or allow Candidate 360, candidate, financial, note, detailed intelligence, other-candidate, or organization reads. Detailed Candidate Intelligence remains consultant-facing during beta, and presentation can later be white-labeled.
- Global approved brands are readable to authenticated members; drafts/review queues require platform roles. Organization notes remain tenant-isolated.

Mandatory negative tests cover list, direct UUID/public ID, nested child, search, relationship expansion, RPC, Storage URL, route manipulation, inserts with foreign organization IDs, updates that attempt to change `organization_id`, and hierarchy mutation/cycles. Consultant A must not retrieve Consultant B's candidate through Candidate 360 or a task, event, message, Discovery, Strategy, or referral ID. A manager must retrieve their own and descendants' records but not records in a sibling branch. Peer consultants remain mutually isolated.

### Future manager operating view

Manager analytics use the same authorized descendant set as candidate operations; they do not introduce a second security model or organization-public records. Authorized projections may provide My Pipeline, a selected descendant's pipeline, All Team, candidate/stage counts, movements, overdue follow-ups, meetings, referrals, awards, conversions, and activity metrics. Aggregate queries must apply the same hierarchy predicate before aggregation so counts cannot reveal sibling-branch data.

## 7. Identity and route strategy

Use database-generated UUIDs as relational primary keys. Keep provider IDs in provider mapping tables with unique `(provider/account, external_id)` constraints. Use opaque random public tokens only for narrowly scoped public flows.

Candidates receive a stable, organization-scoped `public_id` used by `/crm/candidates/[candidateId]`. Existing demo slugs can be imported unchanged as public IDs while their database PKs become UUIDs. New public IDs may be a non-meaningful stable identifier or slug plus collision suffix; renaming a candidate must not change it. Resolution always includes active organization. Legacy `/crm/[id]` routes can resolve the same public ID and redirect canonically.

Human-readable fixture IDs such as `jared-wirsig`, `era-group`, and stable pipeline keys become import keys/public IDs, not foreign keys. Preserve them in `legacy_id` only during migration with organization/source uniqueness. Referral/package/message/task IDs exposed externally should use UUIDs or stable public IDs, not composite strings whose delimiters encode relationships.

## 8. Audit and provenance

Every mutable domain row records creator/updater actor where meaningful. Use a common provenance vocabulary: `consultant`, `ai`, `system`, `provider`, `candidate`, `franchisor`, plus source type/ID, model/algorithm/prompt version, confidence, and timestamp.

Domain tables hold current truth and status. Dedicated history tables hold material transitions and revisions. `candidate_activities` is the human-readable cross-domain feed referencing source records; it must not replace referral delivery attempts, stage history, or intelligence versions.

AI outputs retain input evidence identifiers/hash and generation configuration. Ordinary recommendations, current scores, UI projections, and safely recomputable outputs remain recomputable. Consequential released intelligence is immutable and preserves exactly what the consultant saw and acted on, including historical match score, evidence, algorithm/model version, and release time. A later algorithm may change current intelligence but never rewrites a released decision snapshot. Consultant overrides append a decision with rationale and preserve the original AI output. Discovery facts point to transcript/note/evidence sources. Meeting intelligence is a draft/versioned output until accepted. Referral approval freezes the exact package and released decision snapshot. Provider events retain their provider ID and receipt provenance.

Audit history should be append-only to application roles. Corrections supersede or redact with a recorded reason. Database audit triggers may supplement domain history for privileged changes but should not be the only explanation visible to users.

## 9. Brand Intelligence ownership

Brands and approved governed facts are platform-global. Facts are individually sourced, reviewed, versioned, and presentation-approved; a brand profile is an assembled view of the current approved versions. Franchisor submissions enter a review workflow and never directly replace approved facts. Organization-specific notes, exclusions, and relationships live in tenant join tables.

**Architectural invariant: commercial relationships must not silently influence AI Brand Match or recommendation ranking.** Payments, sponsorship, advertising, referral economics, preferred relationships, and promotional participation are structurally separate, access-restricted, and excluded from scoring repository contracts. Ranking consumes only approved brand facts and candidate evidence. Any commercial/promotional display is explicitly labeled and separate from candidate-fit reasoning. Invariant tests must prove identical candidate/fact inputs produce identical ranking when commercial state changes.

## 10. Provider persistence boundaries

Initial Google Workspace and Microsoft 365 connections are individual consultant connections: the connected account is tenant-scoped for isolation but owned by a specific organization membership, not by the organization identity itself. This supports consultant offboarding and prevents one member from inheriting another's mailbox merely through membership. Preserve future account types for shared inboxes/calendars, delegated accounts, and service accounts. OAuth refresh/access tokens must never be returned to clients or stored in ordinary plaintext columns. Prefer a managed secret vault/KMS reference; if database storage is unavoidable, use envelope encryption with keys outside the database, strict service access, rotation, revocation, and redacted logging. Client secrets and webhook signing secrets belong in deployment secret infrastructure.

Email keeps provider-neutral canonical messages, threads, recipients, links, attempts, and engagement. Provider mappings retain message/thread IDs. Send and webhook operations require durable idempotency. Raw webhook payload retention should be minimal and policy-driven.

Calendar keeps one provider-neutral event. Mappings retain provider event/calendar/account IDs, etag/version, recurring master/instance identity, cancellation/deletion, and last sync. Store IANA timezone plus UTC instants. Sync state stores Google sync tokens or Microsoft delta links securely. Conflict policy should be explicit field ownership plus provider version: never last-write-wins blindly. Recurrence exceptions are first-class mappings, and provider deletion produces canonical cancellation/deletion history rather than silent loss.

## 11. Incremental migration sequence

1. **PERSISTENCE 001 — Identity, tenancy, hierarchy, and authorization harness.** Add auth/profile mapping, organizations, memberships, beta roles/capabilities, self-referencing reporting hierarchy plus history, active-workspace resolution, typed database client, recursive RLS helper strategy/tests, and explicit repository composition. Prove same-organization hierarchy rules, cycle rejection, consultant/peer/manager/admin policy behavior, and demo-mode separation before candidate tables depend on them. Provision a demo organization/hierarchy identity but keep business reads on fixtures.
2. **PERSISTENCE 002 — Candidates, standardized pipelines, assignment history, notes, stage history, activity.** These are foreign-key and authorization roots for nearly every later pack. Apply assignment/ancestor RLS to candidate list, direct/public ID, search, and pipeline content; keep canonical pipeline configuration organization/team standardized. Dual-read verification may compare durable results with fixtures, but writes must have one owner. Preserve public IDs and canonical routes.
3. **PERSISTENCE 003 — Tasks, Calendar, reminders.** Migrate independent work aggregates and their activity links. Establish timezone and assignment patterns before external providers.
4. **PERSISTENCE 004 — Assessment invitations, attempts, responses, results, Candidate Evidence/Intelligence.** Persist raw inputs before outputs; version algorithms and backfill fixture profiles as released snapshots.
5. **PERSISTENCE 005 — Discovery sessions, events, facts, notes/transcript references.** Depends on candidate/evidence/intelligence and calendar identities. Replace request-local session persistence.
6. **PERSISTENCE 006 — Brand core and governed Brand Intelligence.** Establish global ownership, fact versioning/review, organization notes, and scoring isolation before durable strategy snapshots reference fact versions.
7. **PERSISTENCE 007 — Brand Strategy and Presentation.** Persist candidate-brand decisions and presentation events; recompute reasoning while retaining version references.
8. **PERSISTENCE 008 — Referral Studio.** Migrate referrals, immutable package versions, approvals, and delivery attempts after candidate, brand, strategy, and provenance foundations exist.
9. **PERSISTENCE 009 — Communications and connected accounts.** Migrate messages/events/idempotency first, then introduce OAuth/provider adapters and webhooks behind explicit capabilities.
10. **PERSISTENCE 010 — Calendar provider synchronization and operations hardening.** Add connected-calendar state, recurrence/conflicts/jobs, then remove remaining process-local production paths.

Each pack must leave FranGroove buildable, testable, tenant-safe, and compatible with ongoing demo migration. It ships contract tests, RLS tests, migration/backfill tests, and existing E2E coverage, and remains independently reversible at the adapter/routing level without down-migrating user data.

## 12. Demo-mode migration strategy

Use explicit repository composition selected once from validated deployment mode: `production` uses Supabase adapters and must fail closed if unavailable; `conference-demo` uses deterministic fixture adapters plus its isolated overlay; tests choose a declared adapter. Do not fall back automatically based on missing rows, auth failures, or database errors.

During migration, define repository contracts for direct overlay users (Strategy, Referrals, Communications, Assessment/Discovery). Run contract suites against both demo and Supabase adapters. Keep the conference demo tenant explicit and non-production. E2E may initially remain fast and deterministic on demo adapters; add a separate serialized Supabase integration project using ephemeral/local databases and migrations. Later, a seeded Supabase demo tenant can replace the overlay, but only when reset is tenant-scoped, authenticated, transactionally complete, and impossible in production.

Avoid long-lived dual writes. For a pack, backfill, compare reads in shadow diagnostics, switch reads, then switch writes with idempotent reconciliation. Never merge fixture and production results in a production repository.

## 13. Testing strategy

- **Unit:** engines/scoring, normalization, ID resolution, provenance, time conversion, conflict rules; no database.
- **Repository contracts:** identical CRUD, ownership, idempotency, ordering, archive, and not-found semantics for demo and Supabase adapters.
- **RLS:** authenticated SQL/client tests for every operation and role; cross-tenant and same-tenant peer isolation, assigned-consultant access, recursive manager visibility, sibling-branch denial, owner/admin policy, guessed UUID/public ID, nested joins, RPC, Storage, reassignment, hierarchy cycles, and unauthorized hierarchy mutation.
- **Integration:** actual migrations against an empty database; repository/service transactions, constraints, webhook replay, jobs, token expiry, referral/email retries.
- **E2E:** retain current 61 scenarios; add production-adapter smoke flows and organization switching without sharing page/session state.
- **Tenant and hierarchy isolation:** create Organizations A and B with colliding candidate names/emails/public IDs, plus two peer branches inside A. Cross-organization and peer users must never retrieve unauthorized candidates through list, ID/public ID, search, Candidate 360, relationship expansion, route manipulation, task, calendar event, message, Discovery, Strategy, referral, export, analytics, or Storage. Managers see only self plus descendants. Test writes that attach records across organizations or unauthorized branches.
- **Migration:** migrate from every released schema, validate constraints/counts/reference integrity, rehearse rollback-forward, and verify demo legacy-ID backfill and route stability.
- **Concurrency/idempotency:** simultaneous stage moves, task recommendation acceptance, provider sends/webhooks, referral approval/delivery, calendar sync, and retries.

## 14. Production operations

- Version-controlled forward migrations, local/staging application, CI drift detection, generated database types, and reviewed destructive-change procedures.
- Separate immutable reference/demo seed data from production customer data. Seeds must be repeatable and environment-scoped.
- Supabase point-in-time recovery/backups as available, documented restore drills, recovery objectives, and export verification.
- Structured logs with request/job/organization correlation but no secrets or sensitive bodies; error reporting, audit dashboards, webhook/job dead-letter visibility, and database performance/slow-query alerts.
- Use Supabase pooling/serverless-safe clients; no service-role client in browser bundles. Budget indexes and connection concurrency.
- Durable job/queue mechanism for sends, sync, scoring, reminders, and webhook processing; retry with backoff, idempotency, and dead-letter handling. Cron schedules enqueue work rather than performing unbounded work inline.
- Signed webhook verification, replay prevention, receipt logging, secret rotation, and subscription renewal monitoring.
- Retention schedules are configured by data class: long-lived/audit-sensitive candidate history, consultant decisions, referrals, released AI provenance and audit; normal business candidate/task/meeting/communication records; shorter-lived raw webhooks and temporary sync state; special handling for transcripts, recordings, and sensitive imported documents; immediate credential revocation when connections end. Exact legal/product durations are a **REQUIRES PRE-LAUNCH DECISION**, not a blocker for Persistence 001.
- Account/organization deletion is a staged workflow: suspend access, revoke provider tokens, export if required, redact/delete personal data subject to retention, preserve legally required audit, and verify Storage cleanup.

## 18. Persistence 001 implementation record

Persistence 001 implements the approved foundation in `20260820120000_persistence_001_identity_tenancy_hierarchy.sql` without introducing candidate tables. The current hierarchy uses the approved self-referencing `organization_memberships.manager_membership_id` tree plus append-only `membership_reporting_history`. A same-organization composite foreign key rejects cross-tenant managers; a database trigger serializes hierarchy writes per organization and rejects inactive managers, suspending managers with active reports, self-management, immutable identity changes, and direct or multi-level cycles. Another trigger records only actual manager changes and accepts an optional transaction-local reason.

RLS is enabled on profiles, organizations, memberships, and reporting history. Security-definer helpers use an empty search path, schema-qualified relations, no dynamic SQL, active organization/membership checks, and organization-bound recursion. Consultants resolve self only, managers resolve self plus active descendants, owners/admins receive explicit organization administration, suspended memberships resolve nothing, and anonymous roles have no table privileges. Candidate policies will consume this boundary in Persistence 002.

Application code now has a server-only `AuthenticatedWorkspaceContext` data-access boundary and centralized beta role capabilities. `PERSISTENCE_MODE` makes demo versus Supabase selection explicit: development/Playwright may default to demo, production must be explicitly configured and rejects demo. Existing domain repositories remain deterministic demo adapters until their designated packs; there is no database-error fallback to demo.

The admin Supabase client remains `server-only` and is reserved for verified webhooks, controlled jobs, and audited system operations. Ordinary authenticated workspace resolution uses the cookie-bound user Supabase client and RLS. Schema-derived Supabase types are generated from the validated local database into `types/database.generated.ts` and integrated into every Supabase client factory; see `persistence-development.md` for the regeneration workflow.
